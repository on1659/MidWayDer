# MidWayDer 개발방향 판단 프레임워크

> 목적: MidWayDer에서 "이 아이디어가 좋아 보이는가"가 아니라, "이 변경이 프로젝트를 올바른 방향으로 밀어주는가"를 일관되게 판단하기 위한 기준을 문서화한다.

---

## 한 줄 기준

MidWayDer의 올바른 개발방향은
**"기능 수를 늘리는 것"이 아니라, 사용자가 A→B 경로를 최대한 유지하면서 가장 가기 편한 경유지를 더 정확하고 더 쉽게 선택하게 만드는 것"**이다.

즉, 아래 중 하나라도 분명하게 좋아져야 한다.

- 추천 품질
- 선택 속도
- 모바일 사용성
- 계약 안정성
- 검증 가능성

반대로, 겉보기 기능은 늘어나지만 위 다섯 축을 해치면 좋은 방향이 아니다.

---

## MidWayDer의 북극성

MidWayDer는 일반적인 장소 검색 앱이 아니다.

핵심은:

1. 사용자의 **주 경로를 최대한 유지**한다.
2. "가장 가까운 곳"이 아니라 **가장 가기 편한 곳**을 추천한다.
3. 사용자가 **짧은 시간 안에 믿고 선택**할 수 있어야 한다.

따라서 어떤 변경이든 아래 질문으로 시작한다.

### 제일 먼저 물을 질문

이 변경은 아래 중 무엇을 더 좋게 만드는가?

- Detour 기반 추천의 정확도
- 추천 결과의 이해 가능성
- 검색부터 선택까지의 사용자 흐름
- 모바일에서의 탐색/비교 편의성
- 데이터/API/알고리즘 계약 안정성
- 테스트와 회귀 검출 능력

명확한 답이 없으면 우선순위를 낮추거나 보류한다.

---

## 판단 5축

## 1. Mission Fit

가장 중요한 축이다.

### 핵심 질문

- 이 변경이 "가장 가기 편한 경유지"를 더 잘 찾게 하는가?
- 사용자가 결과를 더 잘 믿고 선택하게 만드는가?
- MidWayDer의 차별점인 detour 기반 가치와 연결되는가?

### 높은 점수를 주는 변화

- Detour 계산 정확도 개선
- 추천 정렬 근거 설명 강화
- 잘못된 추천 감소
- 의미 있는 fallback 개선
- 결과 비교를 더 쉽게 만드는 UI

### 낮은 점수를 주는 변화

- 핵심 추천 품질과 무관한 기능 추가
- 표면적인 장식만 늘어나는 UI 변경
- "있으면 좋지만 핵심 가치와 멀다" 수준의 확장 기능

---

## 2. User Flow Fit

MidWayDer는 검색 엔진이 아니라 의사결정 보조 도구다.
그래서 사용자가 실제로 "찾고, 보고, 비교하고, 고르는" 흐름이 더 쉬워져야 한다.

### 핵심 질문

- 검색 → 결과 확인 → 지도 확인 → 선택 흐름이 더 짧고 자연스러워지는가?
- 결과를 읽는 데 필요한 인지 부담이 줄어드는가?
- 모바일에서 첫 화면과 주요 액션이 더 선명해지는가?
- 오류/빈 상태/로딩 상태가 덜 혼란스러워지는가?

### 높은 점수를 주는 변화

- 모바일 결과 카드 정보 우선순위 개선
- 지도와 리스트 상호작용 안정화
- 빈 상태 / 에러 상태의 이해 가능성 개선
- 결과 비교를 위한 정보 구조 개선

### 경계해야 할 변화

- 카드에 정보만 계속 추가해서 높이와 복잡도만 늘리는 경우
- 데스크톱에선 좋아 보여도 모바일에서 흐름이 망가지는 경우
- 새로운 상태를 추가했는데 fallback이 없는 경우

---

## 3. Contract Safety

MidWayDer는 여러 층이 얽혀 있어서, 방향이 좋아 보여도 계약을 흔들면 결국 나쁜 방향이 된다.

### 반드시 지켜야 할 대표 계약

- `src/app/api/**` request / response shape
- `src/lib/map-provider/**` 공통 인터페이스
- `src/lib/detour/**` 점수 의미와 정렬 기준
- `src/store/**` 주요 store shape
- `src/locales/**` key 체계
- 모바일 핵심 플로우
- offline/cache 동작 기대치

### 핵심 질문

- 이 변경이 계약을 추가하는가, 바꾸는가, 깨는가?
- 하위 호환성을 유지하는가?
- 관련 계층을 같이 업데이트할 수 있는가?
- 문서/타입/테스트가 계약 변화를 따라가는가?

### 높은 점수를 주는 변화

- 계약을 더 명확히 만드는 타입/검증 추가
- provider abstraction을 유지하면서 내부 구현을 개선하는 변경
- 응답 shape를 안전하게 확장하는 변경

### 낮은 점수를 주는 변화

- API/타입/스토어 shape를 조용히 바꾸는 변경
- map provider 공통 계약을 임시 편법으로 우회하는 변경
- i18n/offline 등 주변 계층을 무시한 부분 최적화

---

## 4. Evidence and Measurability

좋은 방향은 "좋아 보임"이 아니라, 적어도 일부는 증거로 확인돼야 한다.

### 핵심 질문

- 이 개선이 실제로 나아졌다는 증거를 만들 수 있는가?
- 기존 회귀를 잡을 테스트나 지표가 있는가?
- 없다면 최소한 어떤 검증 계획이 있는가?

### MidWayDer 기본 증거

- `npm run lint`
- `npm run type-check`
- `npm run test`
- `npm run test:e2e:smoke`
- `npm run test:e2e:mobile:ui`
- `npm run test:e2e:mobile:visual`
- 대상 영역의 Vitest
- Playwright MCP 캡처

### MidWayDer 핵심 지표

- API 응답 시간 `< 3초`
- PostGIS 쿼리 `< 200ms`
- 거리 오차 `±5%`
- 시간 오차 `±10%`
- 모바일 UI 회귀 없음

### 높은 점수를 주는 변화

- 테스트가 같이 생기는 변경
- 추천 품질 비교 기준이 명확해지는 변경
- 회귀를 자동으로 잡는 QA 자산을 늘리는 변경

### 낮은 점수를 주는 변화

- 검증 계획 없이 "체감상 좋아졌다"로 끝나는 변경
- 중요 플로우 변경인데 모바일 검증이 없는 경우
- 성능/품질 변화가 있는데 지표가 없는 경우

---

## 5. Complexity vs Value

MidWayDer는 이미 알고리즘, API, 지도 UI, i18n, offline이 얽혀 있다.
그래서 복잡도 증가는 매우 신중해야 한다.

### 핵심 질문

- 이 변경이 늘리는 복잡도에 비해 가치가 충분한가?
- 핵심 경로를 안정화하기 전에 주변 기능만 늘리는 것은 아닌가?
- 새로운 상태/계층/옵션을 추가하면서 운영 부담만 키우는 것은 아닌가?

### 좋은 변화

- 기존 흐름 안에서 가치를 크게 올리는 변경
- 추상화는 유지하면서 구현을 단순화하는 변경
- 회귀 위험을 줄이는 정리/정돈

### 나쁜 변화

- 핵심 문제 해결 없이 옵션/설정/토글만 늘리는 변경
- 아직 검증도 안 된 구조를 더 일반화하는 변경
- 하네스/아키텍처 자체를 과설계하는 변경

## 바로 쓸 수 있는 판단 게이트

모든 큰 변경은 아래 순서로 판단한다.

## Gate 1. Mission Gate

질문:

- MidWayDer 핵심 가치에 직접 연결되는가?

판정:

- `yes`: 다음 게이트로 진행
- `weak`: split 또는 보류 고려
- `no`: 우선순위 낮춤 또는 no-go

## Gate 2. Contract Gate

질문:

- 깨지면 안 되는 계약이 무엇인지 식별했는가?
- 그 계약을 유지하거나 안전하게 이행할 계획이 있는가?

판정:

- `clear`: 다음 게이트로 진행
- `unclear`: `/meeting`에서 먼저 정리
- `unsafe`: no-go 또는 재설계

## Gate 3. Evidence Gate

질문:

- 성공/실패를 무엇으로 검증할 것인가?

판정:

- `measurable`: 진행 가능
- `partial`: 조건부 진행
- `none`: 구현 전 검증 계획부터 필요

## Gate 4. Complexity Gate

질문:

- 가치 대비 복잡도 증가가 감당 가능한가?

판정:

- `worth it`: 진행
- `maybe`: 더 작은 범위로 split
- `not worth it`: 보류

---

## 최종 판정 4종

회의나 설계 검토의 결론은 아래 넷 중 하나로 귀결한다.

### 1. Go

조건:

- Mission fit이 강함
- 계약과 검증 계획이 명확함
- 복잡도 대비 가치가 충분함

의미:

- `/build`로 넘겨도 된다

### 2. Conditional Go

조건:

- 방향은 맞지만, 선행 조건이 필요함

예시:

- API shape 명세 먼저
- 모바일 fallback 먼저 정의
- 테스트 케이스 먼저 추가

의미:

- 조건 충족 후 `/build`

### 3. Split

조건:

- 큰 방향은 맞는데 한 번에 너무 많은 층을 흔듦

예시:

- 1단계: 응답 필드 추가
- 2단계: UI 노출
- 3단계: 모바일 최적화

의미:

- 작은 작업들로 쪼개서 진행

### 4. No-Go

조건:

- 핵심 가치와 거리가 멂
- 계약 위험이 큼
- 검증 계획이 없음
- 복잡도만 늘어남

의미:

- 지금은 하지 않는다

## 현재 MidWayDer에서 우선순위가 높은 방향

2026-04-14 기준으로, 아래 방향은 "좋은 개발방향"으로 볼 가능성이 높다.

### 1. 추천 품질 안정화

- Detour 계산 정확도
- proximity / ranking 설명 가능성
- 잘못된 추천 감소

### 2. API 계약과 입력 검증 강화

- route validation
- 응답 shape 일관성
- 에러 처리 명확화

### 3. 모바일 UX 안정화

- 결과 카드 밀도 조정
- 지도/리스트 상호작용
- 모바일 회귀 방지

### 4. map-provider 추상화 보존

- provider 교체 가능성 유지
- 공통 타입과 fallback 보존

### 5. offline / i18n / cache의 깨짐 없는 통합

- locale 누락 방지
- 캐시 fallback 안전성
- 오프라인 상태의 일관성

### 6. QA와 근거 축적

- 회귀 자동 검출
- 모바일 시각적 검증
- 성능/품질 지표 축적

---

## 현재 우선순위가 낮은 방향

다음은 완전히 금지는 아니지만, 지금 시점에선 우선순위를 낮게 본다.

- 핵심 추천 품질과 무관한 장식성 기능
- 모바일 검증 없이 데스크톱 위주로 확장되는 UI
- map-provider / API 계약을 흐리는 빠른 편법
- 검증 계획 없는 대규모 구조 변경
- 의미보다 옵션 수를 늘리는 설정 기능

## 빠른 판단 예시

## 예시 1. 검색 결과 카드에 detour 설명 배지 추가

초기 판단:

- Mission fit: 높음
- User flow fit: 높음
- Contract risk: 중간
- Evidence: 모바일 UI 검증 필요
- Complexity: 중간

결론:

- `Conditional Go`
- 조건:
  - detour 의미와 문구 정리
  - 모바일 카드 높이 확인
  - i18n 키 추가

## 예시 2. 사용자가 테마 색을 8종 고를 수 있게 하기

초기 판단:

- Mission fit: 낮음
- User flow fit: 낮음
- Contract risk: 낮음
- Evidence: 의미 낮음
- Complexity: 중간

결론:

- `No-Go` 또는 후순위

## 예시 3. `/api/search` 응답을 간단히 바꾸고 UI도 같이 맞추기

초기 판단:

- Mission fit: 상황에 따라 다름
- Contract risk: 높음
- Evidence: 필요
- Complexity: 높음

결론:

- 바로 `/build` 금지
- 먼저 `/meeting`
- 가능하면 `Split`

## `/meeting`에서의 사용 방식

`/meeting`은 이 문서를 기준으로 안건을 판정한다.

필수 출력에 아래를 포함한다.

```markdown
## Direction Check
- Mission Fit:
- User Flow Fit:
- Contract Safety:
- Evidence Plan:
- Complexity vs Value:
- Decision: Go / Conditional Go / Split / No-Go
```

---

## `/build`에서의 사용 방식

`/build`는 이미 Go 또는 Conditional Go 된 안건을 실행하는 쪽에 가깝다.
그래도 구현 중 아래가 보이면 다시 설계로 되돌린다.

- 계약 위험이 새로 발견됨
- 증거 계획이 성립하지 않음
- 범위가 과하게 커짐
- 핵심 가치보다 주변 작업이 더 커짐

이 경우 오케스트레이터는:

- `Split` 제안
- `/meeting` 재회부
- must-preserve contracts 재정의

를 해야 한다.

## 최종 원칙

MidWayDer에서 좋은 개발방향은
**"더 많은 것을 만드는 방향"이 아니라, 핵심 추천 가치와 사용자 선택 경험을 더 정확하고 더 안정적으로 만드는 방향"**이다.

그 방향을 벗어나면, 기능이 늘어도 제품은 좋아진 것이 아니다.
