# 장소 주소입력 / 출도착지 입력 UX 결정안

> 작성일: 2026-05-09  
> Route: meeting  
> 목적: 모바일 검색 화면에서 `장소 주소입력` 텍스트박스와 `출발지/도착지` 박스를 동시에 둘지 결정한다.

## 1. 결론

최상단 `장소·주소 검색`란에서 `출발지/도착지`까지 같이 쓰지 않는다.

초기 화면은 하나의 검색 진입점만 둔다.

- 최상단 검색란 라벨: `장소·주소 검색` 또는 `어디를 경유할까요?`
- 역할: 카페, 밥집, 장소명, 주소, 카테고리 검색
- 출발지/도착지는 최상단 검색란과 섞지 않고, 경로가 없거나 사용자가 `경로 수정`을 누른 경우에만 별도 모드에서 노출한다.

즉 사용자가 처음 보는 최상단 검색란은 `경유지/장소를 찾는 칸`이어야 하고, `출발지/도착지를 같이 입력하는 칸`처럼 보이면 안 됨.

## 2. 왜 둘 다 있으면 안 되는가

### 문제

`장소 주소입력`과 `출발지/도착지` 박스가 동시에 보이면 사용자는 아래처럼 해석한다.

- 지금 경유지를 찾는 건지
- 출발/도착지를 먼저 입력해야 하는 건지
- 주소 입력이 출발지인지 도착지인지 경유지인지
- 기존 경로가 이미 있는 상태인지

MidWayDer의 핵심 행동은 `이미 정한 경로 중간에서 어디 들를지 찾기`다. 초기 검색 화면에서 출발/도착 UI가 크게 보이면 이 핵심이 흐려진다.

### 네이버/카카오식 해석

네이버지도나 카카오맵은 목적지가 없는 일반 지도 앱이므로 `검색 → 장소 선택 → 길찾기` 흐름이 자연스럽다.

MidWayDer는 반대로 `출발/도착 경로 → 경유지 추천`이 핵심이다. 그래서 지도 앱의 출도착지 편집 UI를 그대로 복사하면 정보 구조가 꼬인다.

## 3. 상태별 노출 규칙

### A. 초기 / 경유지 검색 진입

보여줄 것:

- 상단 compact search pill
- `어디를 경유할까요?` 입력
- 카테고리 chip
- 최근 검색 / 추천 키워드

숨길 것:

- 큰 출발지 입력 박스
- 큰 도착지 입력 박스
- 교통수단 탭
- 경로 수정 CTA
- 전체 route editor 카드

완료 기준:

- 첫 화면에서 사용자가 `경유지 검색`이라고 바로 이해해야 함.
- `출발지/도착지부터 입력하라`는 느낌이 없어야 함.

### B. 경로가 아직 없는 첫 사용자

출발/도착지가 반드시 필요한 상태라면 `장소 주소입력`과 섞지 않는다.

보여줄 것:

- 별도 `경로 만들기` 진입
- `출발지` / `도착지` 2줄 입력 카드
- 완료 후 경유지 검색으로 이동

원칙:

- 경로 생성 화면과 경유지 검색 화면을 분리한다.
- 한 화면에서 `경로 만들기`와 `경유지 찾기`를 동시에 시키지 않는다.

### C. 사용자가 경로 수정을 누른 경우

이때만 출발지/도착지 박스를 보여준다.

보여줄 것:

- `출발지` / `도착지` 2줄 route card
- 필요 시 swap / 현재 위치 / 삭제 같은 보조 액션
- 저장 또는 적용 CTA

숨길 것:

- 경유지 검색 결과 리스트
- 경유지 카테고리 chip 과다 노출

원칙:

- 출도착지 박스는 `항상 보이는 기본 UI`가 아니라 `경로 수정 모드의 UI`다.

### D. 결과 화면

결과 화면에서는 출발/도착 입력을 다시 크게 노출하지 않는다.

보여줄 것:

- 경유지 결과 하단 시트
- 현재 경로 요약은 작게
- 경로 수정은 보조 버튼으로만 제공

## 4. 문구 결정

초기 검색 입력 문구 후보:

- 1순위: `어디를 경유할까요?`
- 2순위: `중간에 들를 곳 검색`
- 3순위: `장소·주소·카테고리 검색`

사용하지 않을 문구:

- `장소 주소입력`
- `주소 입력`
- `출발지 또는 도착지 입력`

이유:

- `장소 주소입력`은 기계적이고 목적이 불명확함.
- `주소 입력`은 위치 지정 필드처럼 보여서 경유지 검색 의도가 약함.
- 출발지/도착지 문구는 경유지 검색과 섞이면 혼란을 만든다.

## 5. UI 구조 결정

### 추천 구조

```text
[지도]
  └─ 상단 floating search pill
      "어디를 경유할까요?"

[검색 오버레이]
  ├─ compact search input
  ├─ category chips
  ├─ recent/search suggestions
  └─ bottom CTA 또는 선택 결과
```

### 경로 수정 구조

```text
[경로 수정 모드]
  ├─ 출발지 input
  ├─ 도착지 input
  ├─ 이동수단 / 옵션
  └─ 적용 CTA
```

두 구조는 같은 화면에 동시에 full-size로 공존하지 않는다.

## 6. 구현 지침

1. `SearchOverlay` 기본 상태에서 route editor를 제거하거나 접는다.
2. `MobileHomeShell`은 경유지 검색 pill만 강하게 보이게 한다.
3. 출발/도착 입력은 `경로 수정` explicit action 뒤에만 연다.
4. 기존 경로 요약이 필요하면 한 줄 summary로만 보여준다.
5. E2E는 모바일 375px 기준으로 첫 viewport에 출발/도착 입력 박스가 보이지 않는지 확인한다.

## 7. 완료 판정

아래가 모두 만족되어야 완료다.

- 초기 모바일 화면에 `출발지` / `도착지` full input card가 보이지 않는다.
- 검색 입력의 목적이 `경유지 찾기`로 읽힌다.
- 경로 수정은 별도 action 없이는 열리지 않는다.
- 첫 화면에서 사용자가 해야 할 일이 하나로 보인다.
- 기존 네이버식 route card는 `경로 수정 모드`로만 제한된다.

## 8. 최종 결정 문장

초기 검색 화면에는 `장소 주소입력` 하나도 애매하므로 `어디를 경유할까요?`로 바꾼다. 출발지/도착지 박스는 필요하지만 항상 보이면 안 되고, 경로가 없거나 사용자가 경로 수정을 누른 경우에만 별도 모드로 보여준다.
